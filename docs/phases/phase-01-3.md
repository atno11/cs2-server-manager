## Storage design and migration

`internal/storage` owns `instances.db`, SQL statements, versioned schema, migration marker, file checks, bounded operations, and `instances.lock`. The manager still validates definitions and owns all process state, handles and logs. Storage has no process or HTTP responsibilities. The manager uses a three-method persistence boundary to inject deterministic write failures in tests; normal use has one concrete SQLite store.

Schema version 1 uses `PRAGMA user_version=1`. `instances` contains `id TEXT PRIMARY KEY`, `executable TEXT`, `work_dir TEXT UNIQUE`, `port INTEGER UNIQUE CHECK(1..65535)`, and `args_json TEXT CHECK(json_valid(...))`, with `NOT NULL` constraints. `migration_state` has a single completion row. Initialization creates schema and version in one transaction. Unsupported newer versions and unexpected unversioned schemas fail. A missing or empty legacy JSON file still records completed migration. The manager reads legacy JSON through its existing 512 KiB, 32-definition, compact 16 KiB/definition, duplicate-key, ownership and policy validation path, then imports all rows and the completion marker in one transaction. The original JSON file is not modified. Once marked complete, only SQLite is read; deleting every instance cannot trigger reimport. Failed validation or import leaves the completion marker absent and permits a corrected retry. Invalid SQLite never falls back to stale JSON.

The database URI is built with URL escaping for trusted runtime paths, including `?` and `#`. One connection is configured with a 1000 ms busy timeout, DELETE journal mode, FULL synchronous mode, foreign keys ON, and in-memory SQLite temp storage; startup verifies the effective values. Operations use two-second contexts. SQL values are parameters. The private database, lock and rollback journal are checked for regular-file ownership and mode; unsafe existing paths and unexpected WAL sidecars fail explicitly. A nonblocking advisory `flock` on `instances.lock` rejects a second manager for the same runtime directory. This relies on a local filesystem with functional advisory locks and trusted operators who do not remove the lock file or modify SQLite directly while the manager runs.

## Backup, rollback and limitations

Before upgrading, stop the manager, back up the private runtime directory (including `instances.json`, `instances.db`, `policy.json` and `admin.token`) with owner-only permissions, and verify the copy. SQLite's rollback journal should not be copied mid-transaction; stop the manager first. To retry a failed migration, correct the legacy input or filesystem issue and restart; do not delete a database with completed migration. To revert to an older JSON-only binary, restore a pre-migration backup or explicitly export the desired current SQLite definitions into a private JSON file. The retained original JSON may be stale after SQLite changes and must not be treated as a faithful rollback snapshot. This phase does not encrypt definitions at rest, adopt processes after restart, or validate native CS2 execution. Abrupt power loss durability depends on the local filesystem honoring SQLite's sync and rename assumptions. Direct external SQLite writes and hostile same-UID filesystem changes remain outside the supported model.
