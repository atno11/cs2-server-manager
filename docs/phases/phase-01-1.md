## Pre-change static audit

LC-01, LC-02, LC-03, LC-04, LC-05, LC-06, LC-07, LC-08, LC-09 and LC-10 are visible in the checkout. They are static findings until a focused test reproduces the relevant behavior. In particular, `Restart` has a gap between `Stop` and `Start`; `Stop` has an unbounded receive after `Kill`; child-only signals cannot supervise descendants; `Close` is sequential and has no shared completion; `Remove` lacks a closed guard; `Args` crosses ownership boundaries by slice reference; and HTTP shutdown is not awaited before manager cleanup.

## Reproduction and implementation

The three baseline tests remained unchanged. The new `TestUnexpectedLeaderExitCleansDescendant` failed before its targeted fix: the leader exited with code 0, but an inherited stdout descriptor caused `exec.Cmd.Wait` to return `exec.ErrWaitDelay`, which was classified as failed. The fix treats that specific condition as successful only when `ProcessState.Success()` is true, after attempting process-group cleanup. Other preliminary LC findings were confirmed by static inspection, then covered by new regression tests after the initial lifecycle edit. Pre-fix failures for those findings were not captured because those tests were added after the edit; this limits the reproduction claim.

Each instance has one reserved lifecycle operation (`start`, `stop`, or `restart`). Competing operations on the same instance return an error immediately; independent instances can proceed. `Restart` owns its reservation through stop and start, including for an already stopped instance. `Remove` rejects active instances and in-progress operations. `Register`, `Remove`, `Start`, `Stop`, and `Restart` reject mutations after shutdown begins. Input and returned `Args` slices are cloned. Process completion updates an entry only when its process pointer still matches.

State transitions: registration begins `stopped`; a successful launch becomes `running`; stop begins `stopping`; graceful completion becomes `stopped`; unexpected exit 0 becomes `stopped`; unexpected nonzero exit, launch failure, forced termination, signal failure, and termination timeout become `failed`. A failed instance can start again when no process remains attached. Forced stop and timeout failures are returned and retained in `Instance.Error`.

Each child is launched in its own Linux process group (`Setpgid`). Stop signals that owned group with SIGTERM, waits up to two seconds, sends SIGKILL, then waits up to two more seconds. `exec.Cmd.WaitDelay` bounds output draining to one second after leader exit. A waiter attempts group cleanup before clearing ownership and closing completion. `Close` marks the manager closed, waits for already reserved operations, stops active instances concurrently, and lets simultaneous callers wait for the same completion channel. HTTP serving waits for `Shutdown` completion before calling `Manager.Close`; HTTP shutdown has a 15-second deadline. Stop waits are not performed under the registry mutex.

Process groups do not guarantee cleanup of descendants that detach, call `setsid`, or otherwise escape the group. Abrupt manager termination can leave processes behind. A rare group-ID reuse race after leader reaping cannot be ruled out with process-group signaling alone. A kill or wait that fails to complete within the finite bound leaves an observable failed state but may leave a live process; no process adoption is attempted. The bounded in-memory log retains the most recent 64 KiB per instance. The HTTP API still has the previously documented local security and JSON persistence limitations.
