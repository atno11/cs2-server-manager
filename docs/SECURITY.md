# Local security model (Phase 1.2)

This release serves one trusted local administrator on a numeric loopback address. The administrator controls `policy.json`, the runtime directory, server installations, and their configuration files. HTTP instance definitions, websites viewed in the administrator's browser, and unauthenticated local clients are untrusted. The manager runs as a non-root Unix user. Public HTTP exposure, multiple administrators, remote hosts, hostile same-UID processes, and recovery after abrupt manager termination are unsupported.

## Browser and API boundary

A random 256-bit bearer credential is generated in `admin.token` (0600) on first start. No default credential exists. The operator enters it into the browser page or supplies it via `Authorization: Bearer` in a programmatic request. The page keeps it in memory only. There is no cookie or URL credential. Every `/api/` route, including reads and logs, requires authentication. Authentication uses constant-time comparison. Host must match the configured numeric loopback authority exactly. Origin, when present, must match the corresponding `http://` origin; cross-site Fetch Metadata is also rejected. Forwarded headers are ignored. No permissive CORS response is sent. These checks reject simple cross-origin POSTs as well as preflighted requests. The root HTML is a public, data-free login shell.

The server caps connections and active requests at 64 each, header bytes at 8 KiB, JSON bodies at 16 KiB, and uses 5-second header, 10-second read, 15-second write, and 30-second idle deadlines. Registration permits at most 32 instances, 32 caller arguments of at most 256 bytes each, and 4096 total caller argument bytes. JSON rejects unknown fields and trailing values. Routes use exact methods. Invalid requests do not register a partial instance.

## Execution and filesystem boundary

Only local operator policy can authorize executable paths and executable/working roots. The file is mode 0600 in an owner-only runtime directory. Policy roots and instance paths must be absolute, clean, and free of symlink components. Working directories must be owned by the manager user and not group/world writable. Executable trees and files must be owned by root or the manager user and not group/world writable. The manager records file device, inode, and SHA-256 digest at startup; it reopens and verifies before each launch, then executes the opened descriptor through `/proc/self/fd/3`. A changed executable fails closed until operator review and manager restart. Equivalent working-directory identities are rejected with `os.SameFile`; a replacement after registration also fails at start.

The HTTP `args` field is restricted to positional tokens using ASCII letters, digits, underscore, period, slash and hyphen, and cannot start with `-` or `+`. Operator `base_args` may carry trusted CS2 options; the manager appends the managed `-port` argument last and rejects `-port` or `+hostport` prefixes in base arguments. This is a structural policy for accepted forms, not a claim to model every CS2 configuration mechanism. Indirect overrides through trusted operator files or game-specific semantics remain the operator's responsibility.

Filesystem identity checks and descriptor launch reduce path replacement risk, but do not create a boundary against a malicious process with the same Unix UID. Such a process can alter policy, token and user-owned work directories or executables; directory replacement between validation and child `chdir` also remains possible under that adversary. The operator must also ensure parent directories above configured roots cannot be replaced by other untrusted users; the manager validates the configured roots and paths beneath them, but does not audit every ancestor directory. Dedicated ownership and installation controls are required for a stronger boundary. Group/world writable paths are rejected, and unsafe existing permissions are never silently changed. The manager requires runtime pidfd group signaling and readable `/proc` before launching a managed executable; an isolated probe is reaped after validation. No unsafe PID/PGID signaling fallback is used. Detached descendants and abrupt manager death remain supervision limits.

## Secrets and logs

Public instance responses contain only ID, port, state and generic error indicators. Paths, arguments and internal errors are omitted. The admin token and operator supplied `known_secrets` are redacted from per-instance captured output, including matches split across writes. Redaction holds a bounded trailing window before publishing text; logs remain limited to 64 KiB per instance. Unknown secret values cannot be detected reliably. Trusted configuration files can contain secrets and must be protected by the operator. Never put credentials in arguments: local process inspection may expose them. No credential is intentionally logged by the manager. This policy does not protect against a process already running with the same Unix UID or against a privileged host administrator.

## Phase 1.2.1 review corrections

The redactor now masks the union of all known-secret match intervals, so overlapping, nested, adjacent and split-write values remain masked regardless of configuration order. It retains at most the longest secret minus one byte of unresolved input between writes, plus bounded chunk processing; published instance logs stay at 64 KiB. The fixed `[REDACTED]` marker itself cannot contain a configured secret. Registration or startup rejects IDs and ports that include a known secret. API response values are explicitly projected to public fields; application-generated errors carry status codes without echoing input or internal text. Static public state and error-indicator values that conflict with a configured secret are rejected during policy compilation. Unknown secrets remain undetectable.

At every start, the configured working and executable roots and the relevant path components are rechecked. The open executable descriptor must still refer to the pinned device/inode, have the pinned SHA-256 content, be regular and executable, be root- or manager-owned, lack group/world write permission, setuid/setgid bits and a `security.capability` attribute. File capability inspection fails closed on unexpected errors. These checks still rely on the Phase 1.2 assumption that untrusted users cannot replace parent directories above configured roots; they do not defend against hostile same-UID changes between verification and execution.

HTTP registration, operator policy and persisted definitions reject duplicate JSON object keys, including case-insensitive aliases. JSON nesting is capped at 64 levels. `instances.json` is read with a 512 KiB cap, at most 32 definitions, and at most 16 KiB per compact definition; each definition is validated before the manager is returned. Invalid state fails startup without modifying the file. Policy input remains capped at 16 KiB. The operator may configure 0–64 known secrets; one internal administrator token is added separately. Paths are capped at 4096 bytes and existing argument limits remain.

Descriptor launch preserves the trusted original path in `argv[0]` while `exec` still targets `/proc/self/fd/3`. A controlled native Go test executable verified `argv[0]`, `/proc/self/exe`, inherited descriptor, per-instance working directory and resource lookup relative to `argv[0]`. This does not establish CS2 or Steam runtime compatibility: native software may use the kernel's executed path, interpreter script path, `AT_EXECFN`, or other resource lookup rules. Native CS2 validation remains PENDING. Go documents `Cmd.Args[0]` and `ExtraFiles` in [os/exec](https://pkg.go.dev/os/exec); Linux documents file capabilities in [capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html) and script execution details in [execveat(2)](https://man7.org/linux/man-pages/man2/execveat.2.html).


## HTTP response contract follow-up

Successful JSON responses preserve their fixed field names and public value types. Fixed protocol names and schema keys are public vocabulary; secret protection applies to accepted instance values, captured logs and application-generated error text, not arbitrary coincidences with those fixed names. Known-secret filtering happens when definitions are accepted and when logs are captured, before HTTP serialization. The HTTP layer no longer passes serialized JSON or log text through the 64 KiB log ring. Successful HTTP output streams without a log-derived size cap; connection and write timeouts still apply. API errors, including unknown paths and methods, have status codes and no response body, preventing application-generated error text from echoing a configured secret. Authentication challenges retain the `WWW-Authenticate` header. This intentionally changes generic error-body text; clients should use status codes. The 64 KiB per-instance log bound and split-write redaction remain unchanged.


## Phase 1.3 database boundary

Definitions are now stored in owner-only `instances.db` inside the existing owner-only runtime directory. The database and `instances.lock` must be regular files owned by the manager user with no group/world permissions. Existing unsafe database or journal sidecars fail startup; WAL sidecars are rejected because this release uses DELETE journaling. New rollback journals are checked before commit. SQLite temporary storage is configured for memory. SQL values are bound parameters, and HTTP errors retain empty bodies. The database is not encrypted at rest. A local operator or process with the manager's Unix UID can still read or modify files; direct external SQLite writes while the manager runs are unsupported. `policy.json` and `admin.token` remain separate private files.

Phase 1.3.1 applies connection-local settings when each physical SQLite connection opens and rejects incompatible version 1 schemas and oversized stored byte values before loading them into Go. Validation assumes the existing single-manager lock and trusted local operator boundary; hostile concurrent external SQLite writes remain unsupported.

## Phase 1.4 event stream boundary

`GET /api/events` uses the existing bearer, exact Host/Origin, Fetch Metadata and request-capacity checks. The browser sends the token through the `Authorization` header and keeps it only in memory. SSE IDs are process-local sequence numbers, never credentials. Public events carry only IDs, ports, states, generic error indicators and sanitized log bytes; paths, arguments and raw internal errors are omitted. The existing redactor finalizes log bytes before publication, including split-write and overlapping secret matches. Eight subscribers and 128 events per queue bound retained stream memory; a full queue disconnects that subscriber instead of silently dropping events. Slow network writes have per-write deadlines. A reconnect starts from a fresh authoritative snapshot and selected-instance retained logs. Logs older than the 64 KiB per-instance ring are unavailable, and unknown secrets cannot be detected.

Phase 1.5.1 gives the Go client an owned transport with no ambient proxy, a 16 KiB response-header cap and bounded per-host connections. The client still sends credentials only in headers and rejects redirects. TUI-SEC01 for Phase 1.6 requires terminal-safe rendering of untrusted logs, including control characters, ANSI/OSC sequences and malformed UTF-8; the API client must preserve sanitized raw bytes and offsets for reconciliation.

The Phase 1.6 TUI reads only an existing owner-only regular `admin.token` file from an owner-only runtime directory. It opens the credential without following a final symlink, validates the open file's ownership and mode, and never puts the token in URLs, arguments or diagnostics. TUI logs are sanitized only in presentation copies: ESC/ANSI/OSC, C0/C1 and formatting controls, malformed UTF-8 and bidi marks become visible escapes before terminal output. The API client's sanitized raw bytes and byte offsets remain unchanged. Other public error and state strings pass through the same presentation guard. The terminal's own trusted styling may still emit control sequences. The supported threat model does not defend against a malicious process with the same Unix UID changing private files or terminal state.

Phase 1.4.1 also caps active SSE HTTP handlers at eight independently of broker subscriptions. A handler keeps its reservation while a disconnected subscriber's network write is still completing. A stream fails with a status-only 503 if its initial write deadline cannot be set; later deadline failures terminate the committed stream. This preserves bounded write behavior when a response writer cannot provide the required deadline capability.

Phase 1.5 makes the validation page opt-in while preserving the same authentication and Host/Origin checks on API routes. The Go client accepts only numeric loopback HTTP endpoints with explicit 64-character lowercase hexadecimal credentials. It rejects URL credentials, extra URL components, redirects and ambient proxies; network and status errors omit response bodies, paths and bearer values. A failed mutating request may have committed before a network failure, so the client does not retry it automatically. The caller should use an authoritative read. The client has no remote-host or TLS mode. Node.js is used only for development validation, not daemon operation.

Phase 1.6 final user-reported terminal security check: simulated OSC, ANSI, BEL and malformed UTF-8 appeared as escaped text, and the clipboard remained unchanged. This supports the physical TUI-W10 acceptance report; automated sanitizer tests and the PTY checks are separate evidence. Native Ghostty Ctrl+Shift+V paste was reported working in registration fields. Ctrl+V was not independently confirmed. Native CS2 validation remains PENDING.
